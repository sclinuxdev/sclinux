## 1. 已定选型总表

| 项 | 决定 | 改动代价 | 依据 |
| :--- | :--- | :--- | :--- |
| 目标架构 | `x86_64` | 高 | 首轮唯一目标；新增架构需重新引导整条工具链 |
| C 库 | **glibc**（GNU 路线） | **极高** | 见 §1.1——机制支持切换，但需并存一套 musl 包集 |
| 基本命令 | **GNU coreutils** | 中 | 与 glibc 同属 GNU 路线 |
| Init | **systemd** | **低** | 见 §1.1——`service.toml` 与 Init 解耦，切换无需重编任何包 |
| udev | `systemd-udevd` | 低 | `virtual/udev` 可切换至 `eudev` |
| 包管理器 | **sage / shc** | — | 见 [SAGE_DESIGN.md](SAGE_DESIGN.md) |
| 根文件系统 | **XFS on LVM thin** | 高 | 见 [INSTALLATION.md §2](INSTALLATION.md) |
| 引导器 | **systemd-boot** | 中 | 见 [INSTALLATION.md §4](INSTALLATION.md) |
| 目录布局 | **/usr merge** | **极高** | 见 §2 |
| 发布模式 | **滚动更新** | 高 | 见 §3 |
| 配方来源 | **翻译 Arch PKGBUILD** | 中 | 见 §4 |
| 显示协议 | **Wayland** | 中 | X11 已冻结，无可行替代 |
| 合成器 | `wmdx`（长期目标） | 低 | 首发可先带现成合成器，不阻塞发行版 |

> **「极高」的含义**：该项一旦变更，仓库中已有的全部二进制包作废，必须整体重编。这类决定应当视为不可逆。

### 1.1 可切换底座与其真实成本

Sage 在设计上就把三个互斥大件做成了可切换的虚拟提供者（见 [SAGE_DESIGN.md §6](SAGE_DESIGN.md)）：

```toml
[providers]
init = "systemd"        # 可选 openrc / runit / dinit / s6
udev = "systemd-udevd"  # 可选 eudev
libc = "glibc"          # 可选 musl
```

修改 `system.toml` 后执行 `sage rebuild`，引擎会比对声明状态与 LMDB 实际状态，对底座包执行原子置换。**本表中的「改动代价」指的不是这个机制是否可用，而是切换后为使系统重新可用所需的额外工作量。** 三者差别很大：

| 提供者 | 切换后还需要做什么 | 代价 |
| :--- | :--- | :--- |
| **`virtual/init`** | **无。** `service.toml` 与 Init 解耦，`sage rebuild` 直接为新 Init 重新生成全部原生服务脚本 | 低 |
| **`virtual/udev`** | 基本无，规则格式高度兼容 | 低 |
| **`virtual/libc`** | **重编仓库中每一个二进制包** | 极高 |

`virtual/init` 正是这套设计兑现价值的地方：换 Init 在传统发行版里是重装级别的操作，在这里是改一行配置加一次 `rebuild`。

`virtual/libc` 之所以是例外，与 Sage 的实现无关，而是 ABI 层面的事实：已编译的二进制在链接时就绑定了 glibc 的符号版本，而 musl 连 `libc.so.6` 都不提供。切换 libc 意味着仓库需要**并存一套完整的 musl 构建包集**——这是仓库层面的工程量，不是一次 `rebuild` 能解决的。

因此本项目**保留 libc 可切换的设计能力**，但首轮只构建 glibc 一套包集；musl 支持在有余力维护第二套包集之前不予提供。

## 2. 目录布局：/usr merge

**决定：采用合并布局。**

```
/bin   → /usr/bin      （符号链接）
/sbin  → /usr/bin      （符号链接）
/lib   → /usr/lib      （符号链接）
/lib64 → /usr/lib      （符号链接）
```

所有实际文件位于 `/usr` 之下，传统路径仅保留兼容用的符号链接。

**理由**：

- systemd 已明确以合并布局为前提，非合并布局需要额外适配且持续踩坑
- 现代发行版（Arch、Fedora、Debian、Ubuntu）均已完成迁移，翻译其配方时无需调整路径
- 使 `/usr` 成为唯一需要快照与回滚的系统目录，与本项目的 LVM thin 方案契合

**为什么代价极高**：它决定每一个包的文件落点。已发布的包若按非合并布局打包，切换时全部需要重打。**因此必须在第一个包发布前定死。**

## 3. 发布模式：滚动更新

**决定：滚动更新，不做定版发布。**

| | 滚动（本项目） | 定版 |
| :--- | :--- | :--- |
| 仓库结构 | 单一仓库，始终为最新 | 每个发行版本一套独立仓库 |
| 上游更新 | 编好即发布 | 需评估、回移补丁、维护多版本 |
| 维护人力 | **一至二人可行** | 需要团队 |

**理由**：定版发布意味着同时维护「稳定分支」与「开发分支」两套包集，并为稳定分支回移安全补丁。以当前人力这不可持续。

**代价**：无「稳定版」承诺，用户始终运行最新构建。这一点应在 README 中对用户明示。

## 4. 配方来源：翻译 Arch PKGBUILD

**决定：以 Arch 的 PKGBUILD 为蓝本翻译为 `recipe.toml`，而非从上游源码从零编写配方。**

**理由**：

- PKGBUILD 中的 `configure` 参数、补丁集与编译选项是社区长期踩坑的产物。从零编写意味着重新踩一遍——`glibc` 一类的包尤其如此
- sage 的包格式 `*.pkg.tar.zst` 本就沿用 Arch 的约定，`recipe.toml` 与 PKGBUILD 的字段可以较直接地对应
- 上游源码 URL 与校验和可直接复用

**注意事项**：

- PKGBUILD 采用 **GPL 兼容许可**，翻译时应保留出处标注
- Arch 的补丁针对 Arch 的布局与依赖，翻译时需核对是否仍然适用
- 不要盲目照搬依赖列表——Arch 的包划分粒度与本项目未必一致

## 5. 源与仓库的分工

这是两个不同的东西，责任归属不同：

| | 内容 | 谁维护 | 位置 |
| :--- | :--- | :--- | :--- |
| **上游源码** | 各项目发布的 tarball | **上游项目** | `recipe.toml` 的 `[source] url` 指向 |
| **二进制仓库** | 编出的 `*.pkg.tar.zst` + `index.toml` | **本项目** | 自行托管 |

### 5.1 上游源码

`recipe.toml` 仅记录 URL 与 SHA256，**不镜像、不托管源码**：

```toml
[source]
url    = "https://ftp.gnu.org/gnu/bash/bash-5.2.37.tar.gz"
sha256 = "9599b22ecd1d5787ad7d3b7bf0c59f312f3bef7c326a6e6789274d6e5d43d1cd"
```

上游发布新版本时，更新这两个字段并重新构建即可。

> SHA256 不是可选项。缺失时 `sage build` 会跳过校验直接使用下载内容——这等于信任任意中间人。

### 5.2 二进制仓库

由 `sage repo index <DIR> <CHANNEL>` 生成索引，随后以静态 HTTP 提供服务。**没有任何外部方会替本项目托管这些包。**

初期托管方案（按启用顺序）：

1. **构建服务器本地目录** —— 开发期最简单，`file://` 即可使用
2. **GitHub Releases / Pages** —— 免费、静态、够用
3. **对象存储 / CDN** —— 有用户规模后再考虑

### 5.3 维护负担的现实

上游每发布一次新版本，本项目就需要「更新配方 → 重新构建 → 重新发布」一轮。这个负担与包数量成正比：

- 门槛 1 的约 10 个包：可控
- 完整桌面发行版的数千个包：**这正是各发行版需要数百名志愿者的原因**

**因此包集规模本身是一项需要主动控制的决策**，而非放任增长。收窄定位（面向特定场景而非通用桌面）是维持可持续性的主要手段。

## 6. 待定事项

以下尚未决定，但均**不阻塞**当前工作，且改动代价较低：

| 事项 | 现状 | 何时需要决定 |
| :--- | :--- | :--- |
| 内核配置 | 计划先沿用 Arch 的 config 保证硬件兼容性，后续再裁剪 | 构建 `linux` 包时 |
| Channel 命名 | 暂定 `core` / `extra` | 发布第一份 `index.toml` 前 |
| `/etc/os-release` 内容 | 未定 | 首次启动前 |
| 版本号方案 | 滚动模式下意义有限，考虑采用日期 | 首次发布前 |
| 默认合成器 | 首发拟采用现成 Wayland 合成器，`wmdx` 作为长期目标 | 有可启动系统之后 |
| 交叉架构支持 | 暂不支持；新增架构需重新引导工具链 | 无明确计划 |
